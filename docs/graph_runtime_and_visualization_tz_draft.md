# Техническое задание

## Проект
Развитие платформы графового описания, исполнения и интерактивной визуализации вычислительных процессов на базе `comsdk` / `comwpc` / `frontend`.

## Статус документа
Черновик ТЗ для планирования доработки ПО и подготовки следующей научной статьи.

## Основание для подготовки
- Текущее состояние репозитория: ядро `comsdk`, Django-модуль `comwpc`, React-фронтенд `frontend`.
- Статья первой версии системы визуализации 2025 года.
- Идея дальнейшего развития: переход от визуализации обхода графа к полноценной платформе исполнения, анализа и оптимизации графовых вычислительных процессов, включая параллельное исполнение и интеграцию C++-компонентов.

---

## 1. Назначение проекта

Разрабатываемое ПО должно обеспечивать:
- формальное описание вычислительных процессов в виде графовых моделей;
- интерпретацию и исполнение этих моделей;
- поддержку иерархических графов, селекторов, циклов и параллельных ветвей;
- интеграцию внешних вычислительных модулей на Python и C++;
- локальное, гибридное и удалённое исполнение ресурсоёмких участков;
- интерактивную визуализацию структуры и хода исполнения графа;
- накопление истории выполнения, трасс, ошибок и метрик;
- использование системы как инженерного инструмента и как экспериментальной платформы для научных публикаций.

---

## 2. Краткая характеристика текущего состояния

### 2.1. Что уже реализовано
- В `comsdk` есть парсинг графов формата aDOT.
- Есть графовая модель: состояния, переходы, селекторы, подграфы, обработка переходов.
- Есть базовый механизм обхода графа и implicit-параллелизм через `array_keys_mapping`.
- Есть инфраструктура локального и SSH-взаимодействия.
- В `comwpc` реализованы импорт графов, хранение графов и подграфов, API для выдачи JSON-представления графа, запуск исполнения, поток событий, история исполнения.
- Во `frontend` реализованы импорт графа, просмотр графа, раскрытие подграфов, отображение истории исполнения, получение live-событий через SSE.
- В первой статье уже описаны динамическая визуализация, события исполнения, иерархии, селекторы, параллельные ветви и архитектура на Django/Celery/Redis/SSE.

### 2.2. Ограничения текущей реализации
- В ядре фактически используется только `SerialParallelizationPolicy`; полноценной архитектуры явных политик параллельного исполнения нет.
- Отсутствует единый слой адаптеров для внешних исполнителей и C++-модулей.
- Нет завершённого контура гетерогенного исполнения: Python-runtime, C++-ядро, удалённые узлы и визуализация не объединены единым контрактом.
- Передача на удалённые вычислители опирается на SSH-подход, что неудобно для масштабируемой оркестрации и обмена данными.
- Событийная модель слишком укрупнённая: в основном `state_enter`, `state_exit`, `complete`, `error`.
- Нет полноценных метрик производительности по ветвям, состояниям, узлам исполнения, объёму данных и времени передачи.
- Нет версионирования графовых моделей, воспроизводимых профилей запуска и сценариев сравнения разных реализаций.
- Нет формализованного механизма выбора исполнителя: Python, C++, локально, удалённо, гибридно.
- Искусственная задержка исполнения для демонстрации визуализации не должна быть частью production-логики и должна быть переведена в режим симуляции.

## 3. Цель доработки

Создать модульную платформу, в которой графовая модель является единым источником истины для:
- описания вычислительного процесса;
- выбора стратегии исполнения;
- запуска локальных и внешних вычислений;
- сбора трассы и метрик;
- интерактивной визуализации и последующего анализа.

Итоговая система должна позволять не только “обходить граф”, но и:
- исполнять разные участки графа в разных вычислительных средах;
- прозрачно отображать это исполнение в интерфейсе;
- накапливать информацию для отладки, оптимизации и публикации научных результатов.

## 4. Границы системы

### 4.1. Входит в контур проекта
- язык описания графовых моделей aDOT и связанные расширения;
- aINI как источник параметров запуска и начальных данных;
- ядро исполнения графа;
- механизм параллелизации;
- механизм интеграции внешних функций и вычислительных модулей;
- C++-компоненты для тяжёлых вычислений;
- транспорт между Python и внешними вычислителями;
- серверная подсистема запуска, хранения и трассировки;
- веб-интерфейс интерактивной визуализации;
- история, replay, сравнение прогонов, метрики;
- тестирование, бенчмарки, документация.

### 4.2. Не входит в первую очередь
- универсальная кластерная оркестрация уровня Kubernetes;
- полноценный BPMN-движок;
- многопользовательская научная платформа общего назначения;
- визуальный графический редактор aDOT “drag-and-drop” как основной способ авторинга.

## 5. Целевая архитектура

### 5.1. Архитектурный принцип
Система должна быть разделена на 5 логических контуров:

1. Контур описания модели.
2. Контур исполнения.
3. Контур вычислительных адаптеров.
4. Контур событий и истории.
5. Контур визуализации и аналитики.

### 5.2. Контур описания модели
Должен включать:
- aDOT-парсер;
- валидатор графа;
- семантический анализатор;
- преобразование aDOT в внутреннее IR-представление;
- поддержку подграфов, селекторов, циклов, параллельных ветвей, аннотаций к исполнению.

### 5.3. Контур исполнения
Должен включать:
- runtime обхода графа;
- диспетчер состояний и переходов;
- политику исполнения для serial/parallel/hybrid режимов;
- планировщик задач;
- слой контекста исполнения;
- обработку ошибок, retry, cancellation, timeout;
- режим replay по истории событий.

### 5.4. Контур вычислительных адаптеров
Должен включать:
- Python-адаптер;
- локальный C++-адаптер;
- удалённый C++/native-адаптер;
- адаптер стороннего метода как отдельного процесса или сервиса;
- единый контракт вызова функции вне зависимости от языка и размещения.

### 5.5. Контур событий и истории
Должен включать:
- единый event schema;
- streaming live-событий;
- журнал исполнения;
- метрики;
- хранение истории с привязкой к версии графа и конфигурации запуска.

### 5.6. Контур визуализации
Должен включать:
- структурную визуализацию графа;
- live-подсветку исполнения;
- отображение ветвлений, join-узлов и иерархий;
- сравнение прогонов;
- replay;
- панели метрик и диагностической информации.

## 6. Основные технические решения

### 6.1. Внутреннее промежуточное представление
Требуется ввести внутреннее IR-представление графа, не зависящее напрямую от текущих ORM-моделей и UI.

IR должно включать:
- идентификатор графа и его версию;
- список узлов;
- список переходов;
- тип узла;
- тип ветвления;
- метаданные исполнения;
- тип исполнителя;
- требования по ресурсам;
- схему входных и выходных данных;
- ссылки на подграфы;
- атрибуты трассировки.

### 6.2. Исполнительная модель
Нужно формализовать три уровня исполнения:
- `Serial` — последовательное исполнение.
- `ParallelLocal` — параллельное исполнение на локальной машине.
- `ParallelDistributed` — параллельное/асинхронное исполнение на внешних процессах или узлах.

Также нужен `Hybrid`-режим:
- часть узлов исполняется в Python;
- часть узлов — в C++;
- часть узлов — во внешнем исполнителе;
- визуализация должна показывать, где и как был исполнен каждый узел.

### 6.3. Интеграция C++
Для C++ следует предусмотреть два сценария:

1. Локальная интеграция через Python binding.
Рекомендуемый путь:
- `pybind11` как основной способ связи Python и C++;
- строгие типы входных/выходных данных;
- отдельный модуль для массивных вычислений;
- поддержка NumPy-совместимых буферов без лишнего копирования.

2. Удалённое исполнение как отдельный сервис.
Рекомендуемый путь:
- отдельный worker/service;
- бинарный обмен сообщениями;
- независимый runtime;
- возможность запускать вычисления на другой машине.

### 6.4. Транспорт между Python и внешними исполнителями
На уровне ТЗ предлагается заложить слой `ExecutionTransport`, не привязанный к одному протоколу.

Базовый рекомендуемый вариант для прототипа:
- `ZeroMQ + MsgPack`.

Причины:
- хорошая совместимость Python/C++;
- низкие накладные расходы;
- простая схема для request/reply и push/pull;
- удобен для передачи массивов и структурированных сообщений.

Альтернативный вариант для дальнейшего развития:
- `gRPC + protobuf` в случаях, когда важнее жёсткая контрактность и межсервисная стандартизация.

SSH следует оставить только как legacy-механизм или вспомогательный канал.

### 6.5. Канал событий в UI
Для отображения live-хода исполнения в первой итерации можно сохранить `SSE`, так как он уже встроен в текущую систему.

В перспективе нужно предусмотреть возможность перехода на `WebSocket`, если потребуется:
- двустороннее управление исполнением;
- пауза, resume, step-by-step;
- потоковая подгрузка диагностических данных;
- синхронное сравнение нескольких прогонов.

## 7. Функциональные требования

### FR-1. Импорт и валидация графовых моделей
Система должна:
- импортировать `.dot` и `.adot` графы;
- импортировать связанные подграфы;
- импортировать и валидировать `.aini`;
- сохранять исходные тексты модели;
- формировать человекочитаемые сообщения об ошибках синтаксиса и семантики;
- поддерживать dry-run валидацию без сохранения графа в БД.

### FR-2. Версионирование моделей
Система должна:
- хранить версию графа;
- хранить версию aINI;
- фиксировать хэш исходного описания;
- связывать каждый запуск с конкретной версией модели;
- поддерживать сравнение версий модели.

### FR-3. Исполнение графа
Система должна:
- запускать исполнение графа по API;
- принимать начальные данные;
- поддерживать последовательное исполнение;
- поддерживать исполнение с подграфами;
- поддерживать исполнение с селекторами;
- поддерживать циклы и join-узлы;
- позволять прерывать выполнение;
- фиксировать итоговое состояние и ошибку.

### FR-4. Явная параллелизация
Нужно реализовать не только implicit-параллелизм по массивам, но и явную модель параллельных ветвей.

Требуется:
- определить правила split/join;
- определить семантику завершения ветви;
- определить правила объединения результата;
- определить конфликтующие записи в данные;
- поддержать как минимум стратегии:
  - `all_of`;
  - `any_of`;
  - `first_success`;
  - `quorum`;
  - `barrier_join`.

### FR-5. Политики исполнения
Каждый узел или подграф должен иметь исполняемую политику, например:
- `python_local`;
- `cpp_local`;
- `worker_local_process`;
- `worker_remote`;
- `auto`.

Режим `auto` должен выбирать исполнителя по правилам:
- размер данных;
- оценка стоимости вычисления;
- наличие C++-реализации;
- доступность удалённого узла;
- ограничения по памяти и времени.

### FR-6. Контракт функции/обработчика
Для каждого обрабатывающего узла должны быть определены:
- имя функции;
- модуль или адрес исполнителя;
- тип исполнителя;
- схема входных данных;
- схема выходных данных;
- политика ошибок;
- требования по ресурсам;
- флаг трассировки данных;
- флаг возможности replay.

### FR-7. Схема событий исполнения
Нужно расширить событийну модель. Система должна публиковать события типов:
- `execution_started`;
- `execution_finished`;
- `execution_failed`;
- `state_enter`;
- `state_exit`;
- `state_wait`;
- `state_skipped`;
- `branch_spawned`;
- `branch_joined`;
- `remote_dispatch_started`;
- `remote_dispatch_finished`;
- `data_snapshot_created`;
- `warning`;
- `metric`.

Каждое событие должно содержать:
- `session_id`;
- `graph_id`;
- `graph_version`;
- `state_id`;
- `state_name`;
- `parent_graph_id`;
- `branch_id`;
- `executor_type`;
- `worker_id` или `host_id`;
- временную метку;
- длительность или промежуточный тайминг;
- пользовательскую нагрузку события;
- флаг ошибки;
- ссылку на снимок данных при необходимости.

### FR-8. История и replay
Система должна:
- сохранять историю событий каждого запуска;
- позволять повторно воспроизводить прогон;
- показывать состояние графа на выбранном событии;
- сравнивать два прогона;
- строить timeline исполнения;
- экспортировать историю в JSON/CSV.

### FR-9. Визуализация структуры
Интерфейс должен:
- отображать граф целиком;
- поддерживать вложенные подграфы;
- раскрывать подграф в модальном окне и/или отдельном уровне навигации;
- показывать типы узлов различимым образом;
- поддерживать крупные графы и progressive rendering;
- поддерживать фильтрацию по типу узлов, статусу, исполнителю, ветви.

### FR-10. Визуализация исполнения
Интерфейс должен:
- подсвечивать активный узел;
- подсвечивать активные переходы;
- визуально различать completed, running, waiting, failed, skipped;
- показывать параллельные ветви разными каналами;
- показывать где узел исполнен: Python, C++, remote;
- отображать длительность узла;
- показывать диагностические сообщения и исключения;
- показывать историю данных или ссылку на snapshot.

### FR-11. Метрики и аналитика
Система должна собирать:
- время исполнения по узлу;
- время ожидания;
- число ветвей;
- объём переданных данных;
- объём данных на входе и выходе узла;
- тип исполнителя;
- число ретраев;
- количество ошибок;
- загрузку CPU/RAM по возможности;
- эффективность offload в C++/remote.

### FR-12. Входные данные и формы запуска
На основе aINI система должна:
- строить форму запуска;
- поддерживать типизацию параметров;
- поддерживать значения по умолчанию;
- валидировать пользовательский ввод;
- сохранять профиль запуска;
- позволять повторный запуск по профилю.

### FR-13. Диагностика ошибок
Система должна:
- сохранять стек ошибки;
- показывать узел, на котором произошла ошибка;
- различать ошибки парсинга, исполнения, транспорта, сериализации и C++-модуля;
- поддерживать повторный запуск с того же профиля;
- позволять выгружать отчёт об ошибке.

## 8. Нефункциональные требования

### NFR-1. Производительность
- Накладные расходы трассировки должны быть управляемыми и отключаемыми.
- Система должна поддерживать большие графы без полной деградации UI.
- Должна быть возможность переключения между режимами “полная трасса” и “облегчённая трасса”.
- Для выбранных массивных вычислений C++-реализация должна давать измеримый выигрыш относительно Python-базовой реализации.

### NFR-2. Масштабируемость
- Архитектура должна допускать добавление новых исполнителей без переписывания ядра.
- Число удалённых worker-узлов должно масштабироваться горизонтально.

### NFR-3. Надёжность
- Потеря одного remote worker не должна приводить к повреждению общей истории исполнения.
- История запуска должна сохраняться даже при потере live-канала визуализации.
- Должен существовать recovery-механизм для зависших задач.

### NFR-4. Расширяемость
- Должна существовать plugin-like схема регистрации новых обработчиков и новых executor-типов.
- Формат событий и IR должен быть расширяемым без поломки старых клиентов.

### NFR-5. Безопасность
- Нельзя исполнять произвольные небезопасные модули без явного разрешения.
- Для remote execution должны быть предусмотрены аутентификация, авторизация и журналирование.
- Нужно предусмотреть белые списки модулей/функций и режим sandbox для опасных обработчиков.

### NFR-6. Воспроизводимость
- Каждый запуск должен быть связан с версией графа, aINI, исполняющих модулей и средой исполнения.
- Для benchmark-режима результаты должны быть воспроизводимы.

### NFR-7. Переносимость
- Python-часть должна работать в Linux и Windows.
- C++-часть должна иметь воспроизводимую сборку.
- Remote protocol не должен зависеть от SSH как обязательной технологии.

## 14. Основные риски

- Неопределённая семантика параллельного join для сложных графов.

## 17. Что в новой статье действительно может считаться научной новизной

Важно: научная новизна должна опираться на формализацию, алгоритмы, критерии выбора и результаты экспериментов, а не только на “мы сделали UI лучше”.

### Реалистичные варианты научной новизны

1. Метод формального согласования графовой модели и гетерогенного исполнения.
Суть:
- каждому узлу графа сопоставляется не только функция перехода, но и исполняемая политика;
- граф становится не только моделью вычисления, но и моделью диспетчеризации.

2. Метод динамической трассировки и визуализации иерархических и параллельных ветвей исполнения.
Суть:
- вводится формальная событийная модель исполнения;
- строится алгоритм синхронного отображения ветвей, join-узлов, подграфов и ошибок.

3. Метод адаптивного выбора исполнителя для узла графа.
Суть:
- выбор между Python, локальным C++ и удалённым вычислителем производится по признакам задачи;
- оценивается выигрыш и стоимость переключения.

4. Метод replay и сравнительного анализа прогонов графовой модели.
Суть:
- история исполнения хранится так, чтобы можно было реконструировать состояние;
- сравниваются два запуска одной модели при разных стратегиях исполнения.

5. Метод визуальной диагностики “узких мест” графового вычислительного процесса.
Суть:
- метрики и структура исполнения связываются с графовой моделью;
- появляется формальный способ локализовать bottleneck на уровне узлов и ветвей.

### Что не стоит выдавать за научную новизну без дополнительных результатов
- перенос фронтенда на React;
- замена одного транспорта на другой сама по себе;
- просто подключение C++ без новой модели выбора и оценки;
- просто хранение истории в БД;
- просто подсветка активного узла.
